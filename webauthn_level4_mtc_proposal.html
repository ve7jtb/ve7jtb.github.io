Section 1

Background, Problem Statement & Motivation

1.1 The Post-Quantum USB HID Transport Ceiling ($7,609\text{ Bytes}$)

Under CTAP 2.0 through 2.3, USB Human Interface Device (HID) framing enforces an unfragmented single-message payload ceiling of $7,609\text{ bytes}$ (one 57-byte CTAPHID_INIT packet plus up to 128 59-byte CTAPHID_CONT continuation packets):

$$\text{Max Payload} = 57 + (128 \times 59) = 7,609\text{ bytes}$$

When authenticators transition from classical elliptic-curve signatures (ES256, Ed25519) to NIST post-quantum module-lattice algorithms standardized in FIPS 204 (ML-DSA) and draft FIPS 206 (FN-DSA), cryptographic public keys and signatures expand by more than an order of magnitude:

  • ML-DSA-44 (Category 2): $1,312\text{ B}$ public key, $2,420\text{ B}$ signature.
  • ML-DSA-65 (Category 3): $1,952\text{ B}$ public key, $3,309\text{ B}$ signature.
  • ML-DSA-87 (Category 5): $2,592\text{ B}$ public key, $4,627\text{ B}$ signature.

1.2 Failure of Classical X.509 packed Attestation with Post-Quantum CAs

In the standard WebAuthn packed attestation statement format (§8.2), the authenticator transmits an X.509 certificate chain (x5c). With post-quantum CAs:

  • A single ML-DSA-44 intermediate certificate adds $\sim 3,850\text{ B}$.
  • A 2-certificate ML-DSA-87 chain reaches $15,065\text{–}22,693\text{ B}$.

Even with a minimal single-certificate chain, classical X.509 packed attestation exceeds the 7,609-byte USB HID limit for all ML-DSA parameter sets ($7,924\text{ B}$ for ML-DSA-44, $10,982\text{ B}$ for ML-DSA-65, and $14,898\text{ B}$ for ML-DSA-87), causing packet drops and failure on standard desktop USB stacks.

1.3 How Merkle Tree Certificates (MTC) Solve Post-Quantum Scaling

Based on draft-ietf-plants-merkle-tree-certs, Merkle Tree Certificates replace heavy ASN.1 X.509 signature chains with compact, hash-based Merkle inclusion proofs over a transparency log tree.

By defining fmt: "mtc", WebAuthn Level 4 enables:

  1. $100\%$ USB HID Compatibility: All 5 NIST post-quantum algorithms fit within single-message budgets ($3,832\text{–}7,470\text{ B}$ for fmt: "mtc").
  2. Stateless Authenticator Flash: Authenticators derive the public key on-the-fly from a 32-byte TRNG seed, avoiding flash storage exhaustion.
  3. Clean Enterprise Attestation: Binds physical device serial numbers natively via the CA Merkle leaf commitment and manufacturer manifests without wire extension overhead.

Proposed Changes to §8: Defined Attestation Statement Formats

We propose adding the normative attestation statement format identifier mtc to the WebAuthn Level 4 §8 registry:

cddl
; Proposed addition to WebAuthn Level 4 §8: Attestation Statement Formats
$$attStmtType //= (
    fmt: "mtc",
    attStmt: mtcStmtFormat
)

2.1 Merkle Tree Certificate Statement Format (fmt: "mtc")

  • Attestation Statement Format Identifier: "mtc"
  • Attestation Types Supported: Basic, AttCA, Enterprise.
  • Wire Representation (mtcKeyRef): attStmt.mtcCert carries only the ultra-compact 2-field key reference { caId, serial }. The attestation public key (coseKey), validity window (notBefore, notAfter), optional firmwareVersion, and optional mtcProof are omitted from attStmt on the wire and resolved out-of-band by the Relying Party via FIDO MDS3 (MtcTrustAnchor.batchKeys), the manufacturer's enterprise inventory manifest, or in-band via the mtcDebug (mtc-debug) registration extension.

Syntax (CDDL)

cddl
mtcStmtFormat = {
    alg: COSEAlgorithmIdentifier,
    sig: bytes,
    mtcCert: mtcKeyRef
}

mtcKeyRef = {
    caId: bytes,                      ; 1-4 byte compact CA Log Identifier
    serial: uint                      ; Log entry serial number = (logNumber << 48) | index
}

Required Metadata (mtcTrustAnchors[].batchKeys[]) & Manifest Entry Fields

Because attStmt.mtcCert on the wire contains only { caId, serial }, each entry in mtcTrustAnchors[].batchKeys[] (and Enterprise manufacturer manifests) provides:

  • serial (uint): 64-bit log entry serial number (logNumber << 48) | index.
  • notBefore (uint): Unix timestamp (seconds).
  • notAfter (uint): Unix timestamp (seconds); 253402300799 (9999-12-31T23:59:59Z) if non-expiring.
  • coseKey (Base64URLString): Canonical CBOR-encoded COSE_Key structure (per RFC 9052 §7). Because the COSE algorithm identifier (alg, label 3) is embedded inside the COSE_Key structure, a separate top-level alg property on batchKeys[] is redundant and omitted.
  • firmwareVersion (uint, optional): Authenticator firmware version (CTAP 2.3 parameter 0x0E).
  • mtcProof (Base64URLString, optional): Binary RFC 9162 Merkle inclusion proof.
  • deviceSerial (DOMString, optional): Hardware serial number (Enterprise manifest only).
Important

Non-Expiring Device Attestation (notAfter = 253402300799): When the attestation key provisioned on an authenticator has no well-defined expiration date (i.e., the hardware attestation should never expire), notAfter MUST be set to 253402300799 (0x3AFF44417F), which is the Unix epoch timestamp (in seconds) corresponding to 9999-12-31T23:59:59Z (GeneralizedTime 99991231235959Z per RFC 5280 §4.1.2.5 and IEEE 802.1AR IDevID).

  • Cross-Format Consistency: Matches the notAfter lifetime convention already used in X.509 (x5c) batch and enterprise attestation certificates when an authenticator supports both "packed" and "mtc".
  • ECMAScript / WebIDL Safe Integer Precision: 253402300799 ($< 2^{38}$) fits well within IEEE 754 double-precision exact integers (Number.MAX_SAFE_INTEGER = 9007199254740991, $2^{53} - 1$), avoiding the silent rounding corruption that UINT64_MAX (0xFFFFFFFFFFFFFFFF) would suffer when serialized through WebIDL unsigned long long and PublicKeyCredential.toJSON() before reconstructing the 8-byte big-endian not_after field in FidoMtcLogEntry.
Note

Manufacturer Considerations for firmwareVersion in the MTC Manifest: Manufacturers should weigh operational simplicity against cryptographic assurance when deciding whether to populate firmwareVersion in the MTC leaf (FidoMtcLogEntry) and manifest:

  • Omitting firmwareVersion: Allows a single Merkle tree rootHash and batch key to be used across multiple firmware releases, avoiding the need to issue a new batch key or publish a new checkpoint or caId when minor firmware revisions are released under a stable AAGUID.
  • Including firmwareVersion (Recommended): Because firmwareVersion is cryptographically committed as an immutable field in FidoMtcLogEntry, deploying a new firmware version requires issuing a new attestation batch key and leaf serial, which in turn requires generating a new signed subtree checkpoint (rootHash) or caId in FIDO MDS3 or the manufacturer manifest. However, binding firmwareVersion to the batch key is more secure: it cryptographically attests the exact firmware version that generated a credential and allows Relying Parties to selectively revoke or flag a vulnerable firmware build via revokedSerials without distrusting patched authenticators that share the same AAGUID.

Relying Party Verification Procedure for fmt: "mtc"

(For the complete 6-level trust chain diagram and exact byte layouts of FidoMtcSubtreeCheckpoint, FidoMtcLogEntry, RFC 9162 Merkle nodes, and verificationData, see FIDO MDS3 & WebAuthn Level 4 MTC Cryptographic Trust Chain Architecture.)

Given (attStmt, authenticatorData, clientDataHash):

  1. Verify attStmt conforms to mtcStmtFormat ({ alg, sig, mtcCert: { caId, serial } }).
  2. Compute $\text{verificationData} = \text{authenticatorData} \parallel \text{clientDataHash}$.
  3. Resolve the attestation key entry (pubKey, notBefore, notAfter, optional firmwareVersion, optional mtcProof, and optional deviceSerial):
    • Extract (attStmt.mtcCert.caId, attStmt.mtcCert.serial).
    • In non-enterprise mode: query FIDO MDS3 mtcTrustAnchors[caId].batchKeys for serial to obtain the canonical CBOR-encoded COSE_Key structure (coseKey), notBefore, notAfter, optional firmwareVersion, and optional mtcProof.
    • In enterprise mode: query the local manufacturer's inventory manifest for serial to obtain coseKey, notBefore, notAfter, optional firmwareVersion, optional mtcProof, and deviceSerial.
    • Alternatively, if authenticatorData.extensions["mtc-debug"] is present, extract the canonical CBOR-encoded COSE_Key structure pubKey (matching the batchKeys[].coseKey format), notBefore, notAfter, optional firmwareVersion, mtcProof, optional rootHash, and optional deviceSerial.
  4. Verify that the alg parameter (3) inside the COSE_Key structure pubKey matches attStmt.alg, and verify attStmt.sig over $\text{verificationData}$ using pubKey and attStmt.alg.
  5. Verify validity dates: check that $\text{notBefore} \le \text{now} \le \text{notAfter}$ from the resolved metadata/manifest entry (or mtc-debug).
  6. Verify revocation: verify serial is not in revokedSerials.
  7. Verify tree commitment:
    • If mtcProof is present (in the resolved metadata/manifest entry or in authenticatorData.extensions["mtc-debug"]): walk the sibling hashes from SHA-256(pubKey) up to the landmark rootHash published in MDS3 (or mtc-debug.rootHash in offline conformance mode).
    • Otherwise, verify that the RP previously authenticated the complete manifest or MDS batchKeys table against the Root CA signature over rootHash.

Proposed Changes to §10: Defined Extensions (mtcDebug / mtc-debug)

We propose registering the mtcDebug extension in the W3C WebAuthn Level 4 Defined Extensions Registry (§10).

text
WebAuthn Level 4 Extension Identifier: mtcDebug
CTAP2 Extension Identifier:           mtc-debug
Extension Scope:                      Authenticator Extension
Extension Type:                       Registration only (navigator.credentials.create)

3.1 WebIDL Definitions

    required ArrayBuffer pubKey;          // Canonical CBOR-encoded COSE_Key

    unsigned long        firmwareVersion; // CTAP 2.3 parameter 0x0E

    ArrayBuffer          rootHash;        // 32-byte Landmark / Trust Anchor root hash
};

    required Base64URLString pubKey;          // Base64url-encoded COSE_Key
    DOMString                deviceSerial;    // Present ONLY if Enterprise Attestation (EP) is active
    unsigned long long       notBefore;       // Unix timestamp (seconds)
    unsigned long long       notAfter;        // Unix timestamp (seconds); 253402300799 (9999-12-31T23:59:59Z) if non-expiring
    unsigned long            firmwareVersion; // CTAP 2.3 parameter 0x0E
    Base64URLString          mtcProof;        // Base64url-encoded RFC 9162 Merkle inclusion proof
    Base64URLString          rootHash;        // Base64url-encoded 32-byte root hash

}

3.3 Processing Rules

Important

mtcDebug (mtc-debug) Permitted Only When fmt: "mtc" (Explicitly Disallowed for "none" and Other Formats): Because authenticatorData.extensions["mtc-debug"] is embedded inside authenticatorData (which is exposed to the Relying Party even when fmt is "none"), mtc-debug MUST NOT be requested, emitted, or accepted when attestation or fmt is "none" or any format other than "mtc".

Client (Browser/Platform) Processing:

  1. Request Gate (navigator.credentials.create()): If extensions.mtcDebug === true:
    • If options.publicKey.attestation is "none" (including when omitted and defaulting to "none"), if the platform/user agent replaces the attestation conveyance preference with "none" (e.g., due to user consent or policy), or if options.publicKey.attestationFormats is present, non-empty, and does not contain "mtc", the platform MUST NOT pass mtc-debug in the CTAP2 authenticatorMakeCredential extension inputs.
    • Otherwise, pass mtc-debug: true into CTAP2 authenticatorMakeCredential.
  2. Response Gate: Upon receiving the authenticator response, if authenticatorData.extensions contains "mtc-debug":
    • If the attestation statement format (fmt) in attestationObject is "none" or is not "mtc", or if the platform replaces the attestation statement with "none", the platform MUST NOT expose clientExtensionResults.mtcDebug and MUST reject the response (aborting the ceremony with NotAllowedError), ensuring authenticatorData.extensions["mtc-debug"] is never returned to the Relying Party when fmt !== "mtc".
    • Otherwise (when fmt === "mtc"), parse authenticatorData.extensions["mtc-debug"] and expose pubKey, deviceSerial, notBefore, notAfter, firmwareVersion, mtcProof, and rootHash in clientExtensionResults.mtcDebug.

Authenticator Processing:

  1. If mtc-debug is requested:
    • Attestation Format Gate: If the attestation statement format (fmt) selected by the authenticator for this registration operation is "none" or any format other than "mtc", the authenticator MUST ignore mtc-debug and MUST NOT include "mtc-debug" in authenticatorData.extensions.
    • Otherwise (when fmt is "mtc"):
      • Set bit 7 (ED, 0x80) in authenticatorData.flags.
      • Include the active attestation pubKey (batch key if non-enterprise, single-device key if enterprise).
      • If Enterprise Attestation is active (0x0A = 1 or 2), include deviceSerial.
      • Privacy Gate: If Enterprise Attestation is not active, the authenticator MUST NOT include deviceSerial.
      • Offline Manifest & Diagnostic Mode Support: If configured for diagnostic output or autonomous offline verification in proof-less mtcKeyRef environments, include notBefore, notAfter (253402300799 / 9999-12-31T23:59:59Z per RFC 5280 §4.1.2.5 when the device attestation never expires), firmwareVersion (matching parameter 0x0E in authenticatorGetInfo), mtcProof, and rootHash.

Relying Party / Verifier Processing:

  • Attestation Format Gate: If authenticatorData.extensions contains "mtc-debug" (or clientExtensionResults.mtcDebug is present) when attObj.fmt is "none" or any format other than "mtc", the Relying Party MUST fail the registration ceremony.
  • Test fixtures and automated certification suites inspect mtcDebug.pubKey to perform immediate offline cryptographic verification of attStmt.sig without connecting to external MDS3 infrastructure.
  • In proof-less mtcKeyRef environments, verifiers use notBefore, notAfter, firmwareVersion, and pubKey from mtcDebug to reconstruct the leaf preimage, verify the inclusion proof against rootHash, and authenticate the device completely offline.

Section 4

Proposed Changes to §5: Data Types & Capability Signaling

To allow Relying Parties to signal support for Post-Quantum Merkle Tree Certificate formats during registration, we propose extending attestationFormatsPreference (CTAP2 0x0B) and authenticatorGetInfo (0x16: attestationFormats):

webidl
// WebAuthn Level 4 partial dictionary for CredentialCreationOptions
partial dictionary PublicKeyCredentialCreationOptions {
    sequence<DOMString> attestationFormats;
};

4.1 Size-Aware Default Attestation Selection ("packed" vs. "mtc")

When the Relying Party does not specify an explicit format preference, authenticators implement a size-aware default selection:

  1. Classical Algorithms (ES256, Ed25519): The authenticator returns standard "packed" (x5c), which fits comfortably within the $7,609\text{-byte}$ limit ($500\text{–}1,250\text{ B}$).
  2. Post-Quantum Algorithms (ML-DSA, FN-DSA): The authenticator returns compact "mtc", omitting the multi-kilobyte public key to guarantee that all parameter sets (including Category 5 ML-DSA-87) fit within the $7,609\text{-byte}$ USB HID ceiling without fragmentation ($3,832\text{–}7,470\text{ B}$).
Section 5

Security & Privacy Considerations

5.1 Privacy & Unlinkability on Consumer Registrations

  • In standard non-enterprise registrations (ep = false), fmt: "mtc" uses a shared batch key across $\ge 100,000$ authenticators.
  • No device serial number is committed to the tree or sent on the wire.
  • In mtcDebug, deviceSerial is strictly suppressed on non-enterprise registrations, preventing tracking vectors.

5.2 Enterprise Attestation Without Wire Extension Overhead

  • In Enterprise Attestation (ep = true), the physical serial number is bound directly to the attestation private key through the CA Merkle leaf hash (FidoMtcLogEntry.extensions) and the manufacturer manifest.
  • This eliminates the need for a separate wire serial extension in authenticatorData.extensions, saving $36\text{ bytes}$ and keeping authData at its minimal 70-byte baseline.

Implementation Status & Conformance Evidence

The proposed WebAuthn Level 4 changes have been fully implemented and validated on physical hardware:

  • Authenticator Implementation: Implemented in Fidont (simulator based on Google OpenSK Rust codebase running on Nordic Semiconductor nRF52840 SoC at 64 MHz).
  • FIDO Conformance Tool Verification: Achieved 250 Passed / 0 Failed (100.00% PASS) across all 37 CTAP 2.3 test suites in the official FIDO Conformance Debug Log.
  • Hardware Protocol Analysis: Verified with Zero USB Bus Errors across 127,232 USB packets captured with a Total Phase Beagle USB 480 Protocol Analyzer.
  • Cycle-Accurate Timing: DWT cycle telemetry confirmed that compact fmt: "mtc" attestation completes in 1,655–2,303 ms MCU compute time on constrained Cortex-M4 hardware.
