Section 1

Problem Statement: Why Classical packed X.509 Attestation Breaks for Post-Quantum

In WebAuthn packed attestation, a MakeCredential response carries: (1) authData.attestedCredentialData.credentialPublicKey (the newly generated user credential COSE_Key), (2) attStmt.sig (the authenticator's attestation signature over authenticatorData || clientDataHash), and (3) attStmt.x5c ([attestnCert, ...caCerts], where attestnCert is a DER-encoded X.509v3 certificate containing both the batch/enterprise subjectPublicKeyInfo and the Attestation CA's signatureValue). With classical ES256 (65 B public key, ~71 B signature), a single-cert packed attestation response is ~713 bytes. With post-quantum ML-DSA (FIPS 204) or PQ/T hybrid composites, the wire and NVRAM footprint explodes:

Component in MakeCredential Response Classical (ES256) ML-DSA-44 (-48) ML-DSA-65 (-49) ML-DSA-87 (-50) ML-DSA-87-Ed448 (-56)
authData base + credentialPublicKey ~220 B ~1,470 B ~2,110 B ~2,750 B ~2,810 B
attStmt.sig (Attestation Key sig) ~71 B 2,420 B 3,309 B 4,627 B 4,741 B
attestnCert subjectPublicKeyInfo ~91 B 1,334 B 1,974 B 2,614 B 2,675 B
attestnCert CA signatureValue ~71 B 2,420 B 3,309 B 4,627 B 4,741 B
attestnCert X.509v3 TBS + ASN.1 overhead ~260 B ~280 B ~280 B ~280 B ~280 B
Total (1-cert x5c, no intermediate) ~713 B ~7,924 B ~10,982 B ~14,898 B ~15,247 B
Total (2-cert x5c w/ Intermediate CA) ~1,150 B ~11,960 B ~16,545 B ~22,419 B ~22,943 B
Hardware & Transport Bottlenecks

• CTAP2 maxMsgSize & USB HID Frames: Standard USB HID CTAP2 authenticators advertise maxMsgSize between 1024 and 7680 bytes (the maximum single CTAPHID message payload is 7,609 bytes: 1 init packet of 57 B + 128 continuation packets of 59 B). Even a 1-cert ML-DSA-44 packed attestation (7,924 B) exceeds the 7,609-byte USB HID protocol hard limit!
• Authenticator Flash/NVRAM Budget: Constrained MCUs (such as the nRF52840 in Fidont) store attestation material in flash pages (persist.rs). Storing multi-kilobyte X.509 certificates consumes scarce non-volatile storage.

Section 2

Two New WebAuthn Attestation Formats: mtc and mtc-mds

1. mtc (fmt: "mtc") — MTC Attestation with Inline Public Key

• Carries the attestation public key (pubKey as a CBOR-encoded COSE_Key) inline alongside alg, sig, and mtcCert.
• Use Case: Enterprise Attestation (AttCA), standalone MTCs, or large vendor batch logs where the Relying Party only caches the 32-byte Landmark SubtreeHash [start, end) from MDS.
• Flash Savings on Authenticator: Because Fidont derives pubKey on the fly from the 32-byte attestation private key seed (attestation_key.get_pub_key()), the authenticator never needs to store the 1.3–2.6 KB public key in flash—only the 32-byte seed and the ~150–280 B mtcCert!

2. mtc-mds (fmt: "mtc-mds") — MDS/Log-Assisted MTC Attestation

• Omits pubKey from attStmt on the wire. The Relying Party fetches the batch attestation public key indexed by (mtcCert.caId, mtcCert.serial) from FIDO MDS (mtcTrustAnchors[].batchKeys) or the vendor's MTC issuance log.
• Use Case: Basic Batch Attestation (Basic) for hardware security keys where a vendor has a small number of manufacturing batches per model, and maximum wire compression is required so that even ML-DSA-87 (-50) fits inside a single 7,609-byte USB HID CTAP2 frame.

Wire-Size Comparison Across Formats (2^8 = 256 Batch Log Entries, Landmark Proof = 256 B)

Format ML-DSA-44 (-48) ML-DSA-65 (-49) ML-DSA-87 (-50) ML-DSA-87-Ed448 (-56) Fits USB HID (7,609 B limit)?
Classical X.509 packed (1-cert PQ CA) ~7,924 B ~10,982 B ~14,898 B ~15,247 B ❌ None fit
fmt: "mtc" (Inline pubKey + Landmark MTCProof) ~5,490 B ~7,600 B ~10,200 B ~10,435 B ✅ ML-DSA-44 & ML-DSA-65 fit!
fmt: "mtc-mds" (RP fetches pubKey via MDS/Log) ~4,165 B ~5,635 B ~7,595 B ~7,769 B ✅ ML-DSA-44, ML-DSA-65, & ML-DSA-87 fit!

Note: With 2^4 = 16 batches per model, the Landmark MTCProof inclusion path is only 4 × 32 = 128 B, reducing mtc-mds for ML-DSA-87 to ~7,467 B and ML-DSA-87-Ed448 to ~7,641 B (or ~7,577 B for a 4-batch log).

Normative CDDL Specification, MTCLogEntry Leaf Structure & Relying Party Verification

3.1 fmt: "mtc" & 3.2 fmt: "mtc-mds" (CDDL)

$$attStmtType //= (
    fmt: "mtc",
    attStmt: mtcStmtFormat
)
$$attStmtType //= (
    fmt: "mtc-mds",
    attStmt: mtcMdsStmtFormat
)

mtcStmtFormat = {
    alg: COSEAlgorithmIdentifier,
    sig: bytes,
    pubKey: bytes,          ; Canonical CBOR COSE_Key
    mtcCert: mtcEntryDesc,
} // {
    alg: COSEAlgorithmIdentifier,
    sig: bytes,             ; Self attestation
}

mtcMdsStmtFormat = {
    alg: COSEAlgorithmIdentifier,
    sig: bytes,
    mtcCert: mtcEntryDesc,  ; pubKey fetched via MDS/log
}

mtcEntryDesc = {
    caId: bytes,            ; DER Binary TrustAnchorID (RFC 9879)
    serial: uint,           ; uint64: (log_number << 48) | index
    notBefore: uint,        ; uint64 Unix epoch seconds
    notAfter: uint,         ; uint64 Unix epoch seconds
    ? fwVersion: uint,      ; Optional firmware version
    mtcProof: bytes,        ; TLS-serialized MTCProof (§4.2)
}

4. Deterministic FidoMtcLogEntry & MTCProof

For each batch or enterprise attestation key at index index in log log_number, serial = (log_number << 48) | index. The Merkle tree leaf input (hashed with RFC 9162 0x00 leaf prefix H(0x00 || entry)) binds:

  1. ca_id: Variable-length prefix + caId bytes (ASN.1 DER relative OID / TrustAnchorID).
  2. serial: 8-byte big-endian uint64 ((log_number << 48) | index).
  3. not_before & not_after: 8-byte big-endian uint64 timestamps.
  4. aaguid: 16-byte authData[37..53] (avoiding duplicate transmission in attStmt).
  5. fw_version: Optional 8-byte big-endian uint64 (0 if absent).
  6. pub_key_hash: 32-byte SHA-256(pubKey) over canonical CBOR COSE_Key.
  7. extensions: Length-prefixed MTCLogEntryExtension list from MTCProof.
struct {
    MTCLogEntryExtension extensions<0..2^16-1>;
    uint48 start;
    uint48 end;
    opaque inclusion_proof<0..2^16-1>;
    Cosignature signatures<0..2^24-1>;
} MTCProof;

5. Unified Relying Party Verification Procedure (mtc and mtc-mds)

  1. Decode CBOR: Parse attStmt according to mtcStmtFormat (fmt == "mtc") or mtcMdsStmtFormat (fmt == "mtc-mds").
  2. Handle Self Attestation: When fmt == "mtc" and mtcCert is absent, verify sig over authenticatorData || clientDataHash using credentialPublicKey and return Self.
  3. Resolve Trust Anchor & Attestation Public Key (pubKey): Lookup the MtcTrustAnchor matching mtcCert.caId for authenticatorData.aaguid. If fmt == "mtc", extract attStmt.pubKey; if fmt == "mtc-mds", lookup mtcCert.serial in mtcTrustAnchor.batchKeys.
  4. Verify Attestation Signature: Verify pubKey.alg == attStmt.alg and verify attStmt.sig over authenticatorData || clientDataHash.
  5. Check Validity Period & Serial Revocation: Verify current time is within [notBefore, notAfter], verify serial >> 48 == logNumber, and confirm serial is not in revokedSerials.
  6. Reconstruct Leaf & Verify Merkle Inclusion Proof: Compute pubKeyHash = SHA-256(pubKey), reconstruct FidoMtcLogEntry, compute expectedSubtreeHash via RFC 9162 §2.1.3.2 over (index, start, end, FidoMtcLogEntry, inclusion_proof), and verify it matches an active landmark subtree in mtcTrustAnchor.subtrees.

7.3 3-Tier Size-Aware Default Attestation Cascade ("packed" → "mtc" → "mtc-mds")

When the client omits attestationFormatsPreference (0x0B), Fidont evaluates a 3-tier size-aware cascade so every registration returns the richest self-contained attestation format that fits inside a single 7,609 B USB HID CTAP2 message (<= 7,550 B threshold): Tier 1 ("packed" with x5c) if authData + sig + x5c + 60 <= 7550; Tier 2 ("mtc" with inline pubKey + mtcCert) if authData + sig + pubKey + 260 <= 7550; otherwise Tier 3 ("mtc-mds" with mtcCert only).

Section 8

Enterprise Attestation (0x0A), Signed Device Serial ("fido-mtc-ent"), and Fleet Scaling (100k to 5M+ Keys)

Each physical authenticator is provisioned at manufacturing time with two distinct attestation keys: AttestationId::Batch (shared across >= 100,000 authenticators for non-enterprise privacy) and AttestationId::Enterprise (1 unique single-device keypair per authenticator, selected when enterpriseAttestation 0x0A = 1 or 2, loaded with both a single-device mtcCert and a per-device X.509 x5c certificate containing OID 1.3.6.1.4.1.45724.1.1.2).

8.2 Root CA Subtree Checkpoint (FidoMtcSubtreeCheckpoint)

To cryptographically bind "caId": "g5k_AQI" (and "g5k_AQE") to the ML-DSA-87 Enterprise Root CA in attestationRootCertificates with zero USB wire overhead, each subtree entry in mtcTrustAnchors carries an ML-DSA-87 signature over the 85-byte checkpoint: 

struct {
    opaque context[32];   // "FIDO-MTC-SUBTREE-CHECKPOINT-V1\0\0"
    opaque ca_id<1..255>; // 0x0005 || 83993f0102 ("g5k_AQI")
    uint16 log_number;    // 7
    uint48 start;         // 0
    uint48 end;           // 8 (or 131072)
    opaque root_hash[32]; // 32-byte Merkle subtree rootHash
} FidoMtcSubtreeCheckpoint;

During Enterprise Attestation (0x0A = 1 or 2), the authenticator sets ED (0x80) in authenticatorData.flags and includes "fido-mtc-ent": { "deviceSerial": "123456" } in authenticatorData.extensions, achieving 1:1 parity with X.509 id-fido-gen-ce-sernum (1.3.6.1.4.1.45724.1.1.2):

Evaluation of C509 (draft-ietf-cose-cbor-encoded-cert-21) & Synergies with OpenID Federation 1.1

9.1–9.2 Why C509 Alone Cannot Solve the Post-Quantum 7,609 B USB HID Limit

While C509 compresses ASN.1 DER boilerplate by ~300 bytes (saving 58% on classical ES256 batch certs and ~900 B in NVRAM via lossless Type 3 CBOR re-encoding), C509 cannot compress the high-entropy post-quantum subjectPublicKey or CA issuerSignatureValue (achieving only a 3.8%–4.7% reduction on PQ certificates):

10. Bidirectional Synergies with OpenID Federation 1.1

10.1 Federating FIDO Authenticator Metadata (fido_authenticator)

• Per-AAGUID Resolution (§5.1, §8.1): Replaces monolithic 50+ MB post-quantum MDS3 BLOBs with on-demand Entity Statements for fido_authenticator.
• Protocol Key Separation (§5.2.1): Serves large PQ batchKeys and Root CAs via signed_jwks_uri (application/jwk-set+jwt).
• Certification & Lab Delegation (§7, §7.2, §8.4): FIDO Alliance issues trust-mark-delegation+jwt to accredited security labs, which issue live-revocable trust-mark+jwt statements to authenticator models.
• Historical Keys (§8.7) & RP Privacy (§8.5, §19.2): Enables 10-year hardware token verification across key rollovers (superseded vs. compromised) and privacy-preserving synchronization via federation_trust_mark_list_endpoint.

10.2 Compacting Post-Quantum OpenID Federation trust_chain with MTC

• The PQ trust_chain Bottleneck (§4.3, §4.4, §8.3.2): In OpenID Federation 1.1, every Entity Statement carries both a full jwks public key and a JWS signature, and trust_chain is REQUIRED in Resolve Responses (§8.3.2). A 4-statement ML-DSA chain with delegated Trust Marks reaches 45–62 KB (or 70–100 KB with peer_trust_chain in §4.4).
• MTC-Backed Subordinate Statements & Trust Marks: Publishing an mtc_subtrees checkpoint in the Superior's Entity Configuration replaces the 4.4–6.2 KB Base64URL ML-DSA signature with a ~400–700 B Merkle proof and binds the subordinate key via its 32 B RFC 7638 JWK Thumbprint (kid), reducing each Subordinate Statement from 7.6–10.2 KB down to ~1.1 KB (an 85%–89% reduction per hop).

11. Multi-Level HSS/LMS Certificate Hierarchies (RFC 8554 ∩ NIST SP 800-208) Over Stateless ML-DSA Leaf Keys (x5c) vs. mtc and mtc-mds

11.1–11.2 Non-Enterprise: Pre-Published LMS_SHA256_M32_H5 Intermediates in MDS

• RFC 8554 ∩ SP 800-208 Sweet Spot: Only L=1 with LMOTS_SHA256_N32_W8 (0x04, 1,124 B OTS) fits PQ credentials under 7,609 B; W4 (2,180 B OTS) and on-wire L=2 HSS (2,964 B sig) exceed 7,609 B.
• Offloading Intermediates to MDS: An offline Parent Root CA signs 4–32 LMS_M32_H5/W8 Intermediates (60 B PK, 1,676 B DER cert each) pre-published in MDS. Each Intermediate signs 32 stateless ML-DSA-44 batch keys on demand (zero MDS updates; SP 800-208 §6.1 per-factory HSM isolation), keeping on-wire x5c locked at 3,008 B (1,296 B CA sig).

11.3–11.4 Enterprise 10M–100M Scale (H10 Root → H20 Intermediates) & ML-DSA-65/-87 Impact

• 10M–100M Single-Device Enterprise Hierarchy: An LMS_M32_H10 Parent Root CA (1.07B device capacity) signs 10 (18.4 KB DER for 10.5M devices) to 96 (176 KB DER for 100.7M devices) pre-published LMS_M32_H20/W8 Intermediates (1,048,576 devices each, ~16 s HSM init), yielding a 3,488 B per-device x5c.
• ML-DSA-65 & ML-DSA-87 Leaf Key Wall: Upgrading the leaf batch key adds +1,529 B (-49) or +3,487 B (-50) on the wire, making "packed" x5c exceed 7,609 B for all PQ credentials with -49/-50 batch keys and requiring "mtc" or "mtc-mds".

11.6 Signature Security Comparison: LMS_SHA256_M32 x5c vs. Pure Level-Matched ML-DSA Chains vs. MTC

• NIST Category 5 CA Bit-Security: Every hash in LMS_SHA256_M32 / LMOTS_SHA256_N32_W8 is domain-separated by (I, q, i, j) and a 32-byte randomizer C, so birthday-bound collisions do not apply; forgery requires breaking 256-bit SHA-256 second-preimage resistance (NIST PQC Category 5). Unlike a pure level-matched ML-DSA-44 (Cat 2) or ML-DSA-65 (Cat 3) chain that downgrades the Root/Intermediate CA to Cat 2/3, LMS_SHA256_M32 keeps the CA layer at Category 5 across all tiers while saving 1,124–3,331 B per signature.
• Assumption Diversity vs. Lattice Monoculture: Pairing a hash-based LMS_SHA256_M32 CA (or MTC SHA-256 Merkle tree) with a lattice-based ML-DSA leaf protects 20-year MDS trust anchors from algebraic Module-LWE/SIS breakthroughs.
• Why MTC / MTC-MDS Achieves the Best of Both Worlds: While LMS requires strict single-HSM state isolation (NIST SP 800-208 §6.1) to prevent catastrophic LM-OTS leaf index q reuse, MTC hashes FidoMtcLogEntry directly into the SHA-256 Merkle tree with zero LM-OTS signatures and zero secret/stateful keys, combining Category 5 SHA-256 security with 100% statelessness and an 83 B proof.
