Section 1

Core PIN Protocol keyAgreement Issues & Post-Quantum HPKE Architecture

1.1 Vulnerabilities in CTAP 2.0–2.3 PIN Protocols 1 and 2

In CTAP 2.0 through CTAP 2.3 (§6.5, authenticatorClientPIN 0x06), PIN/UV Auth Protocols 1 and 2 establish a transport encryption channel between the Platform (OS/Browser) and the Authenticator using an ephemeral P-256 ECDH key exchange (getKeyAgreement, subcommand 0x02). This design suffers from four fundamental cryptographic weaknesses:

1. Harvest-Now-Decrypt-Later (HNDL) Quantum Exposure

A passive observer recording USB, NFC, BLE, or IPC traffic today captures the Authenticator's P-256 public key Q_auth, the Platform's public key Q_plat, and the AES-256-CBC ciphertexts. A future CRQC running Shor's algorithm recovers d_auth, derives sharedSecret, and decrypts long-lived static secrets: the user's static PIN hash LEFT(SHA-256(PIN), 16) in pinHashEnc (0x06) and newPinEnc (0x05), the long-lived PPUAT in pinToken (0x02), and static vault/disk encryption keys in hmac-secret (prf).

2. Unauthenticated keyAgreement (Active Bus MITM)

getKeyAgreement (0x02) returns a raw, unauthenticated P-256 public key. An active bus MITM can substitute its own ephemeral keypair on both sides:
• External PIN (0x09): MITM decrypts pinHashEnc in real time to steal LEFT(SHA-256(PIN), 16).
• Internal UV (0x0A): When on-device biometrics are used, there is no shared PIN secret and CTAP 2.3 sends no pinUvAuthParam (0x04) in 0x0A—allowing any bus MITM to hijack the returned pinUvAuthToken!

3. Unauthenticated AES-256-CBC Responses

While requests authenticate ciphertexts via a separate pinUvAuthParam (HMAC-SHA-256), responses such as pinToken (0x02) and hmac-secret outputs use raw unauthenticated AES-256-CBC, leaving response ciphertexts malleable on the wire.

4. Mandatory 1-RTT Overhead on Every Ceremony

Every PIN/UV ceremony requires an explicit getKeyAgreement (0x02) round trip prior to calling 0x09 or 0x0A. With post-quantum KEM public keys (1.2–1.5 KB), fetching an ephemeral key on every login adds substantial latency over NFC and BLE.

1.4 Zero-RTT keyAgreement Caching Against PPUAT_v3 (Skipping getKeyAgreement)

Once a Platform completes initial binding—acquiring PPUAT_v3, receiving the Authenticator's static batch public key pk_batch, and validating the vendor attestation over authenticatorGetInfo (Section 2)—it caches:

CachedBinding = (deviceIdentifier, PPUAT_v3, kemId, pk_batch, VerifiedGetInfoProfile)
1. Saves 1 Full RTT & ~2.5 KB per Login: pk_batch and batchAttestSig are sent only once per computer. Every subsequent login jumps directly from authenticatorGetInfo (0x04) to getPinUvAuthToken... (0x09 / 0x0A), cutting NFC/BLE latency by >50%.
2. Eliminates Runtime ML-KEM.KeyGen on MCU: On bound sessions, the Authenticator never generates PQ keypairs at runtime; it only executes fast ML-KEM.Decaps(sk_batch, enc).
3. Full Per-Session Bidirectional Freshness: Platform samples fresh randomness in KEM.Encap(pk_batch), and Authenticator supplies a fresh 128-bit random IV_id in encIdentifier (0x19) bound as psk_id in HPKE SetupPSKS.
4. Instant O(1) Downgrade Verification: Matching encIdentifier (0x19) lets the Platform immediately verify that received authenticatorGetInfo fields match VerifiedGetInfoProfile without re-running signature verification.

1.5 Open-Source / Privacy Authenticators (aaguid = 016, No Batch Cert), Low-Entropy PINs in Key Agreement & the 8-Try pinRetries State Machine

PQ-PAKE & Anti-Brute-Force

A critical deployment class for pinUvAuthProtocol = 3 includes open-source, DIY, small-vendor, or privacy-focused authenticators that intentionally have no batch attestation certificate (batchAttestSig absent) and an all-zero aaguid (00000000-0000-0000-0000-000000000000) so FIDO MDS lookup is impossible. This raises two fundamental security questions when the user has a low-entropy PIN (e.g., 4–6 digits): (1) Is it safe to make the device PIN part of key agreement? and (2) How must the 8-try pinRetries counter work so neither a malicious Platform nor a fake Authenticator / active MITM can test more than 8 PINs?

Why Naive PIN-in-Key-Agreement (HPKE mode_psk with psk = pinHash) Is Catastrophically Broken Without Attestation

If an unattested authenticator sends an unblinded public key pk_auth in getKeyAgreement (0x02) and the Platform simply feeds psk = LEFT(SHA-256(PIN), 16) into HPKE.SetupPSKS(pk_auth, psk) in 0x09, an active MITM or fake authenticator replaces pk_auth with its own keypair (pk_mitm, sk_mitm). When the user types their PIN once, the Platform encapsulates enc to pk_mitm and sends (enc, pinUvAuthParam). Because the MITM knows sk_mitm, it decapsulates K_kem = ML-KEM.Decaps(sk_mitm, enc) and runs an offline dictionary attack testing all 104–106 PINs against pinUvAuthParam in <1 millisecond—recovering the PIN on the very first attempt while completely bypassing the Authenticator's 8-try pinRetries counter! (Likewise, classical P-256 SPAKE2+ alone fails against an HNDL active MITM with a future quantum computer.)

When It IS Safe: Post-Quantum PAKE via ML-KEM t̂-Vector Blinding (PQ-EKE / CAKE)

Making the low-entropy PIN part of key agreement on an unattested authenticator is cryptographically safe—both classically and post-quantumly—if and only if the Authenticator's ephemeral ML-KEM public key in getKeyAgreement (0x02) is blinded by a salted PIN verifier w before transmission:

1. Salted Verifier (setPIN 0x03): w = HKDF-SHA-256(salt = pinSalt, IKM = LEFT(SHA-256(PIN), 16), info = "CTAP2.3-PINv3-PAKE", L = 32)
2. Blinded getKeyAgreement (0x02): m_w = SampleUniform_Zq(SHAKE256("CTAP2.3-PINv3-PAKE-MASK" || w || rho))
t_blinded = (t_eph + m_w) mod 3329 --> returns (ek_blinded = Encode12(t_blinded) || rho, pinSalt)
3. Platform Unblinding (0x09): t = (t_blinded - m_w) mod 3329 --> (K_kem, enc) = ML-KEM.Encap((t, rho)) + HPKE.SetupPSKS(psk = w)
  • Blocks Offline Guessing by a Malicious Platform (0x02): By Module-LWE (MLWE), t_eph = A*s + e mod 3329 is indistinguishable from uniform random. For every candidate PIN w', (t_blinded - m_{w'}) mod 3329 is a valid uniform public key vector. Calling getKeyAgreement 1,000,000 times leaks 0 bits of offline PIN information.
  • Blocks Offline Guessing by a Fake Authenticator / Active MITM (0x09): To know a secret trapdoor vector s_mitm for the key the Platform encapsulates to, the MITM must commit to a single PIN guess w_guess before sending 0x02. If w_guess != w_user, the Platform encapsulates to t_mitm + (m_{w_guess} - m_{w_user}) = t_mitm + Δ. By Module-SIS / Module-LWE, the MITM cannot decapsulate enc and gets 0 offline guesses!
pinRetries Rule Authenticator State Machine Requirement (Capping Key-Establishment Tries at ≤ 8) Attack Prevented
1. Single-Use dk_eph in getKeyAgreement (0x02) Calling 0x02 does not decrement pinRetries (since t_blinded leaks 0 bits offline), but the Authenticator holds at most 1 armed dk_eph in RAM and immediately wipes dk_eph on the very first 0x09 / 0x04 attempt. Prevents unauthenticated DoS lockout via 0x02 while forbidding reuse of one getKeyAgreement across multiple PIN tries.
2. Write-Before-Verify NVRAM Decrement (0x09 / 0x04) Before executing ML-KEM.Decaps(dk_eph, enc), check pinRetries > 0 (max 8) and bootFailures < 3, and write pinRetries -= 1 to NVRAM first. Only reset pinRetries = 8 after both Decaps and pinUvAuthParam succeed. Prevents USB power-tearing / glitching attacks from getting free PIN guesses; strictly enforces the 8-try lifetime limit (3 per boot).
3. Constant-Time FO Implicit Rejection If the Platform used a wrong PIN w' != w, ML-KEM.Decaps(dk_eph, enc) triggers constant-time Fujisaki-Okamoto implicit rejection (K_kem' = J(z || enc)), causing pinUvAuthParam to fail uniformly with CTAP2_ERR_PIN_INVALID (0x31). Eliminates timing and error-code side channels between lattice unblinding failure and MAC failure.
4. Post-Binding 256-Bit PPUAT_v3 Shield After the first successful PIN ceremony, the Authenticator issues 256-bit PPUAT_v3 and a device-local persistent ML-KEM keypair (pk_local, sk_local). Subsequent sessions require a valid 256-bit PPUAT_v3 outer MAC before touching pinRetries. An active MITM on an already-bound computer gets 0 online guesses at the PIN and cannot decrement pinRetries.

1.6 Multi-Tier Trust Hierarchy: Enterprise Host Auth, Batch Key Pinning, Factory Pairing PINs, Evil-Twin Detection & Dual Channel Modes (Asymmetric Pinning vs. Symmetric PPUAT_v3)

Mutual Auth & Dual Modes

To span locked-down enterprise workstations, personal computers, public kiosks, and batchless open-source authenticators, pinUvAuthProtocol = 3 defines a multi-tier trust hierarchy, a MITM-safe initial setup/reset lifecycle, and two post-pairing channel modes.

1.6.1 Tier 1: Enterprise Mutually Authenticated Key Agreement (Host Auth) Enterprise (Has pk_batch + aaguid)

In high-security environments, enterprise authenticators can be configured to only perform key agreement with an enterprise host that presents a deployed corporate certificate or public key:

  • Provisioning (authenticatorConfig 0x0D, subCmd 0x06: setEnterpriseHostTrustAnchors): Loads trusted Enterprise CA Root keys / host public keys and sets enterpriseHostAuthRequired = true (requires acfg permission, scoped to keys with pk_batch and aaguid).
  • authenticatorGetInfo Advertisement: Advertises options.enterpriseHostAuth: true (mandatory) or false (supported), plus 0x2C: pinUvAuthHostAlgs (e.g., -49 ML-DSA-65, -7 ES256).
  • Early Error at getKeyAgreement (0x02): Host sends 0x09: HostAuthPayload {alg, hostCert, hostNonce, hostSig} over "CTAP2.3-HostAuth" || SHA-256(GetInfo) || hostNonce. If missing or invalid, the Authenticator errors immediately at getKeyAgreement with CTAP2_ERR_HOST_UNAUTHENTICATED (0x3E)!
1.6.2 Tier 2: Batch Key Pinning & Same-Batch Evil-Twin Detection Personal vs. Kiosk

Once a personal Platform pairs with an Authenticator and obtains (PPUAT_v3, deviceIdentifier), it pins pk_batch (like TLS Certificate Pinning):

  • Mandatory PPUAT Revocation on Key Rotation: Authenticators rarely change pk_batch; if a firmware update ever rotates pk_batch, the Authenticator MUST revoke all PPUATs to force a fresh attested handshake.
  • Personal vs. Kiosk: Paired personal devices are 100% immune to MITM. Unpaired/kiosk devices rely on their cached FIDO MDS / Vendor Root trust list.
  • Same-Batch Evil-Twin Defense (makeCredential Substitution): If an attacker tricks a user into using an attacker-supplied device from the exact same batch (identical aaguid + pk_batch) configured with the user's PIN, its encIdentifier (0x19) has a different deviceIdentifier that fails decryption under the user's pinned PPUAT_v3—triggering a prominent "New / Unrecognized Authenticator Detected" UI warning!
1.6.3 Preventing MITM During Initial Setup & Factory Reset: Temporary / Factory Pairing PIN + forcePINChange = true

To prevent an active MITM during initial PIN setup (when an unconfigured device would otherwise accept an unauthenticated setPIN 0x03):

  • Enterprise Devices (Temporary PIN) & Consumer Devices (Random 6-Digit Factory Pairing PIN): Ship with a pre-configured Temporary PIN or a random 6-digit Factory Pairing PIN (printed on a tamper-evident scratch-off card in the box) with forcePINChange: true enabled on first use. First-time setup uses changePIN (0x04) authenticated via the PIN-blinded PQ-PAKE (Section 1.5), blocking any MITM during initial setup!
  • How authenticatorReset (0x07) Solves Setup pinRetries Lockout: If the 8-try pinRetries counter is exhausted during initial setup (or later use), executing authenticatorReset (0x07) resets the Authenticator back to its factory-immutable Pairing PIN (with forcePINChange = true and pinRetries = 8) rather than an unauthenticated blank state.

PPUAT Domain Separation Between PIN Protocols 2 and 3

3.1 The Cross-Protocol Quantum Exposure Dilemma & 3.2 One-Way Hierarchical PPUAT Tree

If an Authenticator returned the same raw 32-byte PPUAT over both Protocol 2 (classical P-256 ECDH) and Protocol 3 (Post-Quantum HPKE), a quantum adversary who records a single Protocol 2 session on a legacy host could break the P-256 ECDH exchange, recover the raw PPUAT, and compromise the Protocol 3 HPKE mode_psk key (psk)! Conversely, storing two independent NVRAM tokens would break single-response authenticatorGetInfo (0x19: encIdentifier and 0x1E: encCredStoreState) compatibility.

from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

def hkdf_sha256(ikm: bytes, info: bytes, length: int) -> bytes:
    return HKDF(algorithm=hashes.SHA256(), length=length, salt=b"\x00" * 32, info=info).derive(ikm)

class AuthenticatorPPUATState:
    def __init__(self, ppuat_v3: bytes, device_id: bytes, cred_store_state: bytes):
        self.ppuat_v3 = ppuat_v3                  # 32-byte NVRAM root secret
        self.device_id = device_id                # 16-byte NVRAM identifier
        self.cred_store_state = cred_store_state  # 16-byte NVRAM state

    def get_ppuat_for_protocol(self, protocol_version: int) -> bytes:
        if protocol_version == 3:
            return self.ppuat_v3
        elif protocol_version == 2:
            return hkdf_sha256(self.ppuat_v3, b"CTAP-PPUAT-v2", 32)
        raise ValueError("Unsupported protocol for PPUAT")

    def build_get_info_encrypted_fields(self, iv_id: bytes, iv_css: bytes) -> tuple[bytes, bytes]:
        ppuat_v2 = self.get_ppuat_for_protocol(2)
        k_id = hkdf_sha256(ppuat_v2, b"encIdentifier", 16)
        k_css = hkdf_sha256(ppuat_v2, b"encCredStoreState", 16)
        enc_id = iv_id + Cipher(algorithms.AES(k_id), modes.CBC(iv_id)).encryptor().update(self.device_id)
        enc_css = iv_css + Cipher(algorithms.AES(k_css), modes.CBC(iv_css)).encryptor().update(self.cred_store_state)
        return enc_id, enc_css
Section 4

Extensions Using Encryption (hmac-secret, largeBlobKey, credBlob, and sign / previewSign5)

4.1 hmac-secret & hmac-secret-mc

• Eliding 1: keyAgreement When pinUvAuthToken Is Present: Saves 1,120–1,568 B on the wire and avoids a second ML-KEM.Decaps() on the MCU by deriving the extension secret directly from HKDF-SHA-256(salt=clientDataHash, IKM=pinUvAuthToken, info="CTAP2.3-PINv3-HMAC-SECRET", L=64).
• 0-RTT uv = false Mode: Encapsulates directly to cached pk_batch + PPUAT_v3 without calling getKeyAgreement.
• 100% RP Length Compatibility: Output inside authenticatorData remains exactly 48 B (1 salt) or 80 B (2 salts) in both AEAD (32B/64B ct + 16B tag) and Export-Only modes.

4.2 Encrypting largeBlobKey (0x07)

• The CTAP 2.3 Flaw: largeBlobKey (0x07 in the outer CTAP response map) is sent in plaintext (32 B) over USB/NFC/BLE, while reading authenticatorLargeBlobs (0x0C) requires no PIN/UV.
• Protocol 3 Fix: Because 0x07 is in the outer CTAP response map (never sent to the RP), the Authenticator encrypts largeBlobKey under the active Protocol 3 session key (turning 0x07 into a 48-byte AEAD/CBC ciphertext).

4.3 Deprecating credBlob (§12.5)

• Unreleased Kerberos KDC Design Intent: credBlob was originally intended to store a hash of the Kerberos KDC certificate to prevent KDC endpoint spoofing during FIDO2 desktop login—a feature that has never been released.
• Security & Size Flaws: Exposes plaintext on the bus without mandatory UV (uv=false), cannot be AEAD-encrypted inside signed authenticatorData, and wastes scarce per-passkey NVRAM and PQ packet budget. Fully superseded by largeBlobs (0x07/0x0C) and hmac-secret (prf).

4.4 The WebAuthn sign (previewSign5) Extension & ARKG — CTAP Bus Security

The WebAuthn sign extension (previewSign5, snapshot 5-SNAPSHOT-2026-09-09T13:45) enables a Relying Party or wallet (e.g., EUDI Wallet) to generate hardware-bound signing keys (generateKey) and produce standalone, raw signatures over arbitrary tbs data (sign), with support for Asynchronous Remote Key Generation (ARKG) (draft-bradleylundberg-cfrg-arkg-08).

Three Severe CTAP Bus Vulnerabilities in Plaintext previewSign5
  • Active Bus MITM "Raw Signing Oracle" (tbs & flags Swap): In CTAP 2.0–2.3, pinUvAuthParam (0x08) covers only clientDataHash (0x02), NOT 0x04: extensions. Because previewSign5 returns a standalone raw signature 6: sig over 6: tbs alone, a bus MITM during any legitimate ceremony can replace tbs_honest with tbs_attacker (or downgrade 4: flags to unattended) and capture a valid hardware-backed signature sig_attacker!
  • Complete Defeat of ARKG Unlinkability on the Bus: Sending static 2: keyHandle (kid), 7: additionalArgs (arkgArgs), 6: tbs, 6: sig, and 7: att-obj in plaintext lets any USB/NFC/BLE observer link 100% of ARKG ceremonies and correlate them to external verifiers.
  • HNDL Quantum Break of Classical ARKG-P256: Recording plaintext pkKem and arkgArgs on the bus allows a future CRQC to break pkKem, recover every blinding scalar τ, and retroactively link all historical EUDI Wallet presentations.
Protocol 3 CTAP Bus Architectural Fixes
  • Mandatory Binding of extensions (0x04) in pinUvAuthParam: Under Protocol 3, pinUvAuthParam = authenticate(pinUvAuthToken, clientDataHash || CBOR(extensions)), and previewSign5 inputs are AEAD-encrypted under the Protocol 3 session (or a uv=0 session to pk_batch / PPUAT_v3).
  • Decoupling Raw 6: sig From Signed authenticatorData (sigCommitment): Store a fixed 32-byte commitment 8: sigCommitment = SHA-256(tbs || sig) inside signed authenticatorData.extensions["previewSign5"] (≤45 bytes!) and move both raw 6: sig and 7: att-obj into AEAD-encrypted unsignedExtensionOutputs["previewSign5"]. This preserves transaction-confirmation binding while hiding sig on the bus and preventing 4.6 KB ML-DSA-87 signatures from overflowing authenticatorData!
