3. Detailed Analysis of Authr-ClientPin2-PinPolicy F-2 Test Logic

3.1 Specification vs. Implementation in Fidont

Per CTAP 2.1 / 2.2 / 2.3 Section 6.5.5.5 (Setting a new PIN):

  • The platform zero-pads newPin into a fixed 64-byte buffer (newPin must be at most 63 UTF-8 bytes so that at least one trailing 0x00 byte terminates the PIN inside the 64-byte plaintext block).
  • The authenticator decrypts newPinEnc using sharedSecret to obtain paddedPin:
  • If the decrypted paddedPin buffer length is not 64 bytes, the ciphertext parameter itself is malformed (CTAP1_ERR_INVALID_PARAMETER (0x02)).
  • If the decrypted paddedPin buffer is 64 bytes (PIN_PADDED_LENGTH), the authenticator strips trailing 0x00 bytes and checks the unpadded PIN length: if no 0x00 byte is present (pin.len() == 64 > 63) or if pin_codepoints < minPINLength, it returns CTAP2_ERR_PIN_POLICY_VIOLATION (0x37).

Fidont implements this in client_pin.rs:67-102:

fn decrypt_pin<E: Env>(
    shared_secret: &SharedSecret<E>,
    new_pin_enc: Vec<u8>,
) -> CtapResult<Secret<[u8]>> {
    let decrypted_pin = shared_secret.decrypt(&new_pin_enc)?;
    if decrypted_pin.len() != PIN_PADDED_LENGTH { // PIN_PADDED_LENGTH = 64
        return Err(Ctap2StatusCode::CTAP1_ERR_INVALID_PARAMETER); // 0x02 (2)
    }
    let len = decrypted_pin
        .iter()
        .position(|&c| c == 0)
        .unwrap_or(decrypted_pin.len());
    let mut result = Secret::new(len);
    result.copy_from_slice(&decrypted_pin[..len]);
    Ok(result)
}

3.2 How ClientPin1 vs. ClientPin2 Construct F-2 and F-3

  • Authr-ClientPin1-PinPolicy.js (F-2 & F-3) — Authr-ClientPin1-PinPolicy.js:112-166: Both F-2 and F-3 generate a 64-byte non-zero PIN inside a 64-byte encryptionBuffer (generateRandomClientPinBuffer(64)). Because decrypted_pin.len() == 64 with no 0x00 terminator, Fidont always returns CTAP2_ERR_PIN_POLICY_VIOLATION (0x37).
  • Authr-ClientPin2-PinPolicy.js (F-2 vs F-3) — Authr-ClientPin2-PinPolicy.js:109-159:
  • F-3 ("Try setting new pin, that is exactly 64 bytes, and check that Authenticator returns error CTAP2_ERR_PIN_POLICY_VIOLATION(0x37)") encrypts a 64-byte encryptionBuffer (16B IV + 64B CT = 80 bytes) and asserts CTAP2_ERR_PIN_POLICY_VIOLATION (0x37).
  • F-2 ("Try setting new pin, that is bigger than 63 bytes, and check that Authenticator returns an error") generates a random-length buffer generateRandomClientPinBuffer(generateSecureRandomInt(64, 128)) and passes it to encryptAES256CBC (cryptodep.js:394-405), which calls cipher.update(messageBuffer) without cipher.final(), truncating the plaintext to ⌊L / 16⌋ × 16 bytes:
  • When L ∈ [64, 79] (24.6% chance), newPinEnc has 64 ciphertext bytes (80B total with IV) → CTAP2_ERR_PIN_POLICY_VIOLATION (0x37).
  • When L ∈ [80, 128] (75.4% chance), newPinEnc has 80, 96, 112, or 128 ciphertext bytes (96..144B total with IV) → CTAP1_ERR_INVALID_PARAMETER (0x02) because decrypted_pin.len() != 64.
  • Updating Authr-ClientPin2-PinPolicy.js:130 to assert.notStrictEqual(ctap2Response.statusCode, CTAP_ERROR_CODES.CTAP1_ERR_SUCCESS) matches the F-2 specification ("check that Authenticator returns an error") and the CTAP 2.1 module.
