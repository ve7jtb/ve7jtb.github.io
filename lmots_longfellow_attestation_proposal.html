Notice: This document is an early architectural proposal for discussion only. It is aligned with the FIDO Client to Authenticator Protocol (CTAP) v2.3 Proposed Standard (2026-02-26) and W3C WebAuthn Level 3, and has not been adopted by the FIDO Alliance or W3C WebAuthn Working Group.

A post-quantum FIDO2/WebAuthn attestation architecture combining 128-byte core state RFC 8554 LM-OTS on resource-constrained Secure Elements with Google Longfellow (GKR layered sumcheck + Ligero over binary extension fields GF(2^k)) on participating host platforms. Section 1

Hardware Layer: 128-Byte Core State & Black-Box Manufacturer Profiles

To allow seamless deployment on resource-constrained Secure Element microcontrollers without storing multi-megabyte hash trees or executing heavy lattice/group-signature schemes on-chip, all bulk tree metadata is eliminated. The authenticator maintains a 128-byte core persistent state (112 B read-only factory flash + 16 B mutable monotonic counters) and derives both its one-time LM-OTS key and its local subtree path nodes on the fly.

1.1 Core Persistent State Layout (128 Bytes Total: 112 B Read-Only + 16 B Mutable)

Key Identifier (I) 32 B Read-Only (Provisioned) Internal RFC 8554 tree/leaf domain-separation binding string.
Batch Root ID 32 B Read-Only (Provisioned) SHA-256 hash of the Batch Master Root Public Key; emitted in CTAP 2.3 responses to anchor the token to its manufacturing batch root.

Subtree Offset ID 8 B Read-Only (Provisioned) Identifies the 214 (16,384-leaf) block boundary assigned to this specific device within the 217 (131,072-device) batch.
Subtree Range Limit 8 B Read-Only (Provisioned) Upper bound parameter enforcing the 16,384 makeCredential registration limit per key.
Reservation Milestone Guard 8 B Mutable (Every Δ signs) Manages state reservation blocks of size Δ in NVM to minimize flash write wear. On power-up or reset, the active RAM counter initializes directly to the Milestone Guard and advances NVM by +Δ before signing, guaranteeing zero index reuse across unexpected USB unplugging or power loss.

1.2 Black-Box Manufacturer Implementation Choices for the 14-Level Device Subtree

100% Opaque to CTAP 2.3, Host Prover & RP

Because the authenticator outputs the exact same 14 sibling hashes (448 bytes) of its 16,384-leaf (214) subtree regardless of how they are computed internally, the internal traversal mechanism is a complete black box to the CTAP 2.3 wire protocol, the Host Longfellow Prover, and the Relying Party. Authenticator manufacturers can choose between two implementation profiles based on their Secure Element's NVM/flash characteristics:

Manufacturer Profile 1

Latency-Optimized (Incremental BDS State in NVM)

Stores a 45-node rolling Buchmann–Dahmen–Szydlo (BDS) traversal buffer (~1,440 B mutable NVM; ~1,568 B total NVM with Core State) and uses ~512 B volatile RAM. Computes the 14 sibling nodes incrementally in ~6.2 ms (6 leaf evaluations / 6,234 SHA-256 blocks worst-case per registration).

Manufacturer Profile 2

Flash-Wear-Optimized (Read-Only Top-7 Subtree Cache)

Keeps mutable NVM strictly to the 128-byte Core State (only 16 B of monotonic counters ever written!) and stores the 128 roots of the bottom 7-level subtrees (128 × 32 B = 4,096 B) in read-only factory flash. Computes the active 128-leaf (27) sub-subtree 100% statelessly in volatile RAM (~320 B stack RAM, ~130 ms / 131,953 SHA-256 blocks) and folds the 128 RO roots in <0.1 ms.

Optional On-Key Batch Path

Self-Contained Roaming (+544 B Read-Only Flash)

Manufacturers may also store the 17 static batch ancestor hashes (17 × 32 B = 544 B) in read-only flash on the authenticator and emit all 31 Merkle path nodes (992 B) in the CTAP 2.3 response (~5.20 KB total), eliminating the host Subtree Token entirely for 100% self-contained roaming across any host device.

Section 2

Component Pipeline, authenticatorGetInfo Signaling & Witness Sourcing (CTAP 2.3 & WebAuthn Level 3)

Before registration, an authenticator supporting this scheme advertises its capability in the CTAP 2.3 authenticatorGetInfo (0x04) response (via attestationFormats 0x16 / extensions), signaling to a participating host platform that it can emit a structured LM-OTS witness for host-side Longfellow proof generation. When authenticatorMakeCredential (0x01) is triggered, processing splits across the isolated hardware domain and the participating host platform:

2.1 The Edge Operation (Security Key — CTAP 2.3 Layer)
  • Post-Quantum Credential Generation: Generates a new ML-DSA-65 keypair (COSE alg: -49, 1,952 B public key) and constructs canonical CTAP 2.3 authData (rpIdHash, flags, signCount, 16-byte AAGUID, fixed 32-byte credentialId, and canonical COSE_Key map).
  • CTAP 2.3 Compliant LM-OTS Signing: Per CTAP 2.3 Section 6.1 and WebAuthn Level 3, reads internal leaf index q, derives the one-time LM-OTS private key (w = 4, p = 67 chains) from the 32-byte Master Seed, and signs the constant-length concatenation authData || clientDataHash (~2,053 B = 33 SHA-256 blocks) in <8 ms.
  • On-the-Fly Subtree Path Derivation: Computes the 14 dynamic sibling nodes (448 B) of its 16,384-leaf (214) device subtree on the fly using either Profile 1 (~6.2 ms) or Profile 2 (~130 ms).
  • Single-Frame CTAP 2.3 Response: Returns ~4.66 KB (or ~5.20 KB with on-key batch path), fitting inside a single 7,609 B USB CTAPHID frame: 0x01 fmt (raw/batch witness format), 0x02 authData, and 0x03 attStmt / 0x06 unsignedExtensionOutputs carrying the 2,180 B LM-OTS signature, 14 dynamic path nodes (448 B), randomizer C, leaf index q, Key ID I, and Batch Root ID.
2.2 The Blinding Operation (Participating Host Platform)
  • Witness Parsing & Zero Host Database: Having detected capability via authenticatorGetInfo, the participating platform intercepts the makeCredential response, parses the LM-OTS signature and 14 on-the-fly dynamic path nodes, and keeps authData untouched. Because the key derives its 14 subtree nodes on the fly, no host SQLite/RocksDB database is required.
  • 31-Node Merkle Path Assembly: Pairs the 14 dynamic path nodes (448 B) from the key with the 17 static batch ancestor hashes (544 B) to form a complete 31-node (992 B) Merkle authentication path to the Batch Master Root.
  • Longfellow Private Witness Packing: Packs the 31-node Merkle path, raw LM-OTS signature (67 × 32 B chains + 32 B randomizer C), Key ID I, and 31-bit leaf index q (controlling left/right child order at all 31 levels) into the private witness of the Google Longfellow circuit.
  • Platform Format Rewriting (fmt Transition): Acting as a local, zero-roundtrip WebAuthn Level 3 Anonymization CA, the platform changes fmt from the authenticator's batch/raw format to the new attestation format string "longfellow-lmots-zk" and replaces attStmt with {batchRootId, zkProof}.
Section 3

Multi-Batch AAGUID Routing & WebAuthn Level 3 Public Input Structure

To support production models where a single 16-byte AAGUID spans multiple distinct manufacturing batches—each tied to an isolated Master Root—the attestation output provides a dynamic routing anchor without compromising user anonymity or mutating authData: 

; WebAuthn Level 3 AttestationObject emitted by a Participating Platform
LongfellowZkAttestationObject = {
    "fmt": "longfellow-lmots-zk",
    "authData": bstr,                  ; Unmodified from Authenticator (includes AAGUID & ML-DSA-65 COSE_Key)
    "attStmt": {
        "batchRootId": bstr .size 32,  ; SHA-256 hash of the Batch Master Root Public Key
        "zkProof": bstr                ; 310-345 KB Google Longfellow GKR+Ligero ZK Proof
    }
}

1. Zero Web IDL Changes

Because WebAuthn Level 3 forbids host modification of authData while explicitly permitting platform replacement of fmt and attStmt, existing browser APIs (getAuthenticatorData(), getPublicKey(), getPublicKeyAlgorithm()) work out of the box with zero Web IDL changes.

2. Relying Party FIDO MDS Resolution

During WebAuthn Level 3 Section 7.1 verification (Verify(attStmt, authData, clientDataHash)), the RP pairs authData.attestedCredentialData.aaguid with attStmt.batchRootId to resolve the exact Master Root anchor in FIDO MDS (e.g., "Titan Batch 2026-B").

3. Batch-Scale Anonymity

Each Master Root covers up to 131,072 (217) authenticators—each supporting 16,384 (214) registrations for over 2.14 billion (231) leaf signatures per batch—eliminating individual token tracking or cross-site correlation.

Section 4

Circuit Optimization for Google Longfellow (GKR SIMD + GF(2^k))

Google Longfellow (GKR layered sumcheck + Ligero over binary extension fields GF(2^k)) is heavily optimized for this FIDO attestation layout by exploiting fixed-bound structural constraints and SIMD data-parallelism across the 67 Winternitz chains:

Optimization 1

Fixed-Bound SHA-256 Pre-Padding (33 Blocks)

Because the 32-byte credentialId, canonical COSE-encoded ML-DSA-65 public key (1,952 B + fixed CBOR header), authData header, and clientDataHash (32 B) have a compile-time constant length (~2,053 B = 33 SHA-256 blocks), all SHA-256 bit-padding logic and block boundaries are hardcoded into Longfellow's circuit configuration.

Optimization 2

Bit-Sliced Winternitz Multiplexing in GF(2^k)

Extracts the w = 4 Winternitz nibbles directly from bit-sliced SHA-256 output wires, computes the 3-nibble checksum, and evaluates conditional step-count multiplexers (selecting between hashing for steps j ≥ a_i and bypassing for j < a_i across 15 steps) natively in GF(2^k) without prime-field bit-decomposition overhead.

Optimization 3

GKR SIMD Parallelism (1,100 Blocks in 47 Layers)

Full verification requires ~1,100 SHA-256 blocks (33 msg + 67 × 15 = 1,005 Winternitz + 34 leaf PK + 31–62 Merkle). Because all 67 Winternitz chains execute identical 15-step subcircuits in parallel, GKR sumcheck evaluates all 67 chains simultaneously as a single SIMD subcircuit of depth 15 (adding only ⌈log2(67)⌉ = 7 sumcheck variables/layer), reducing sequential depth to 47 SHA-256 layers.

Enterprise Direct Attestation Profile (No Host ZK — 25-Level Self-Contained Tree)

When deployed for Enterprise Attestation (AttestationConveyancePreference: "enterprise") where zero-knowledge blinding is not required, where ≥1,000 makeCredential registrations per device (210 = 1,024, h_device = 10) is sufficient, and where manufacturing batches are up to ≥20,000 keys (215 = 32,768, h_batch = 15), the architecture simplifies into a 25-level hierarchical LMS/LM-OTS Merkle tree that operates 100% self-contained on the security key with zero host software or storage.

6.3 Enterprise Wire-Size Comparison with Device Serial Number: Direct LM-OTS vs. fmt: "mtc" + "fido-mtc-ent"

This section compares only the two Enterprise Attestation designs (0x0A = 1 or 2), and both carry the same signed device serial number. The first is this section's 25-level self-contained Direct LM-OTS tree. The second is Enterprise MTC (fmt: "mtc" + "fido-mtc-ent") from the MTC proposal §8.1–§8.3. Non-enterprise batch formats (mtc-mds, batch mtc) are left out because they cannot carry a per-device serial.
